# Code-Review: Clipwell Windows — 2026-06-07

## Bewertungsrahmen

Kein MVVM-Refactoring, kein Feature-Umbau, keine neuen Dependencies.

## Race-Condition-Analyse

| Bereich | Bewertung |
|---------|-----------|
| `_ignoreNextClipboard` | Sicher: gesetzt und gelesen nur auf UI-Thread (Clipboard-Events + Paste-Response) |
| DatabaseService `_gate` | Sicher: alle öffentlichen Methoden sperren konsistent, Monitor ist reentrant |
| OCR-Task → `Dispatcher.Invoke` | Sicher: UI-Update geht durch Dispatcher |
| URL-Preview-Task → `Dispatcher.Invoke` | Sicher: UI-Update geht durch Dispatcher |
| `SettingsService._saveGate` | Sicher: Save() von UI-Thread und Auto-Backup-Thread — Lock vorhanden |
| Hotkey-Registrierung | Sicher: nur von UI-Thread aufgerufen |
| SingleInstance-Mutex + `_showEvent` | Sicher: WaitOne in Background-Task, Dispatcher.Invoke für UI-Interaktion |

**Keine kritischen Race Conditions gefunden.**

## Pfad-Konsistenz

`AppPaths.DataDir` ist die einzige korrekte Quelle. Alle Services nutzen sie korrekt.
**Ausnahme:** `App.LogCrash` referenziert `DatabaseService.DataDir` (identischer Wert, aber unnötige Kopplung) → behoben in Refactoring.

---

## Logging-Bewertung

- Crash-Logging in `LogCrash`: ausreichend, atomar (Lock), sinnvoll.
- `ClipboardProcessor.BuildEntry`: `catch { }` ohne Log — absichtlich, da Clipboard-API häufig wirft (z.B. wenn anderes Programm Clipboard hält).
- `DatabaseService.ImportFromJson`: `catch { }` ohne Log für einzelne Entries — absichtlich tolerant.
- Kein Debug-Logging: Korrekte Entscheidung für Produktions-Tray-App.
